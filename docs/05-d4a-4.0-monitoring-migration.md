# Decide4Action 4.0 Monitoring Migration

This document records the analysis of `D4A-ScheduledMonitor.ps1` (Monitoring 7.12.1, built for Decide4Action 3.9.x) against Decide4Action 4.0 servers deployed by the Decide4Action installer. It lists the changes made in `D4A-ScheduledMonitor-4_0.ps1` (Monitoring 7.13.0, Decide4Action 4.0 edition) and the points to verify on a live 4.0 server.

## What changed in Decide4Action 4.0 that affects the monitor

The analysis used the 4.0 installer design and the 4.0 Watchdog work. These are the facts that matter to the monitor:

- Instances are installed below `<base>\<instance>`, default `C:\Decide4Action\<name>`. A server can host several instances.
- `dbconfig.js` is in `<instance>\API\dbconfig.js`, not `<root>\Services\API\dbconfig.js`.
- `D4AKEY`/`D4AIV` are set on the API service. They are set at machine level only when a key already existed.
- Each instance has its own API port. Port `32167` is no longer guaranteed.
- The API can listen with HTTP or HTTPS (the Watchdog `apiProtocol` setting).
- Services are named per instance by the installer. Their names do not always start with `D4A` or `Decide4Action`.
- nginx, Node-RED, the Node runtime (`<base>\Runtime\node-v<version>\node.exe`), and the Watchdog are machine-wide, below `<base>`.
- The Watchdog is a Node Windows service that logs to `<install root>\logs` in a new format. The PowerShell Watchdog that wrote `Log\TaskSchedulerOutput` is not installed by the 4.0 installer, but it may still run on some servers.
- The Node Watchdog does not check Data Collector event staleness from SQL, so the `LastEventTime` evidence that the 3.9 monitor read is gone.
- The installer plans a Monitoring tab that vendors the monitor under its own folder and may pin its version.

## Findings and changes

| # | Area (3.9 function) | 3.9 behavior | Effect on 4.0 | Change in the 4.0 edition |
|---|---|---|---|---|
| 1 | Self-update (`$script:MonitorReleaseScriptFileName`, `Get-MonitorRemoteReleaseDefinition`) | The channel is chosen by filename; any name other than `D4A-ScheduledMonitor.ps1` follows the legacy `-v5` channel | A new or vendored 4.0 file would never update, or would be replaced by 3.9 code | `# D4A-Monitor-Channel: d4a40` header, `d4a40Monitoring` manifest definition, `monitor-4_0-version.txt`; downloaded scripts from another channel are rejected; `AutomaticUpdateEnabled` opt-out |
| 2 | Database settings (`Get-D4ADatabaseConfigPaths`, `Resolve-DbConfigPath`) | Only `Services\API\dbconfig.js` below the root | Database checks report "no dbconfig.js discovered" | Instance discovery; `<instance>\API\dbconfig.js` for every instance; 3.9 paths kept |
| 3 | Database keys (`Get-D4AEnvironmentSecret`, `Resolve-D4ADatabasePassword`) | Process, machine, or user environment only | Fresh 4.0 installs: password decryption fails, so every database alerts | Adds the API service environment, NSSM `AppEnvironmentExtra`, WinSW `<env>`, and `API\.env`; tries every candidate; validates the decrypted text; logs only the source |
| 4 | Email (`Invoke-DbConfiguredEmail`) | The Node helper inherits the monitor environment | `dbconfig.js` cannot decrypt SMTP settings, so email fails | The matching keys are passed to the helper process only; the installer Node runtime is a fallback |
| 5 | API listener (`Test-ApiListener`) | Hardcoded port 32167 | Alerts "no process listening on 32167" on a healthy 4.0 server | Listening ports discovered from each API service process tree; one check per instance; 3.9 rule key kept healthy for recovery |
| 6 | Direct API performance (`Test-ApplicationPerformance`) | `LocalApiAddress` default `http://127.0.0.1:32167/` | False "all attempts failed" alerts | Default value means "discover"; one target per instance; HTTP/HTTPS fallback with a log-only warning |
| 7 | Local API derivation (`Get-D4AApiUri`, `Get-MonitorApiUris`) | `hostname:1200` maps to port 32167 | API health alerts for local-only sites | Uses the discovered port; IT Tools-stored local `32167` addresses are redirected for the run when nothing listens there |
| 8 | API routes (`Test-WebEndpoint`, `Test-ApplicationPerformance`) | Any non-2xx/3xx is an outage | A route renamed in 4.0 (HTTP 404) becomes a false outage alert | On 4.0 servers, HTTP 404 on API health and direct-API routes is log-only ("reachable, unknown route"); public API routes still alert; routes configurable through `ApplicationPerformanceEndpoints` |
| 9 | Windows services (`Test-D4AWindowsServices`, `Get-DataCollectorWindowsService`) | Name must start with `D4A`/`Decide4Action` | Installer-named services are not monitored at all | Services inside a 4.0 instance folder and the machine-wide Watchdog are added; 3.9 servers keep the exact 3.9 scope |
| 10 | Watchdog evidence (`Test-WatchdogServiceLogs`, `Resolve-WatchdogLogRoot`) | `Log\TaskSchedulerOutput` only | No evidence on 4.0 | New log-only 4.0 Watchdog analysis: restarts, possible restart loops, failures, inactivity; legacy analysis kept and also searched below 4.0 instances |
| 11 | Data Collector health (`Test-DataCollectorWatchdogHealth`) | Reads `LastEventTime` lines written by the PowerShell Watchdog | No Data Collector freshness signal on 4.0 | Read-only, time-limited `P4A_LineMonitoringStatus` query; log-only unless `DataCollectorSqlFreshnessAlerts` is `true`; detects local or UTC timestamps |
| 12 | nginx (`Resolve-NginxErrorLog`) | `Decide4Action-Ngnix`/`-Nginx` below 3.9 roots | Error-rate check silently skipped | nginx service path first, then `<base>` and instance folders, then the 3.9 locations |
| 13 | Windows events (`Test-RelevantWindowsEvents`) | Relevance keyword `32167` | Events about other API ports and instances are missed | Discovered API ports, 4.0 instance names, and Watchdog added |
| 14 | IT Tools deployment (`Show-AddSiteMonitoring`, `New-SiteMonitoringConfigurationObject`) | Always installs the 3.9 monitor into the `Configuration` folder and writes `TaskSchedulerOutput` | Wrong edition, folder, and Watchdog path on 4.0 | Version detection and confirmation; 4.0 template; `<base>\Monitoring`; 4.0 configuration keys |
| 15 | IT Tools version update (`Show-UpdateSiteMonitoringVersion`) | Always uses the 3.9 template | Would cross-grade a 4.0 monitor to 3.9 code; no path for upgraded servers | Release chosen by installed channel; optional 3.9-to-4.0 edition switch with full backup |

Discovery safeguards: a 4.0 instance must be confirmed by a Windows service, the configuration, or `<base>\Runtime`, so copied folders are ignored. Direct-API failures on a discovered address are log-only until `LocalApiAddress` is set. The API listener alerts only when the process and port inventories succeeded, and uses the existing two-run confirmation. On a server without a 4.0 instance, every check behaves exactly like Monitoring 7.12.1.

Unchanged on purpose: notification policy, two-run confirmation, cooldowns, recovery state, maintenance windows, CPU/RAM/disk thresholds, SQL Engine and Mosquitto checks, TLS inspection, rule keys of existing checks, the JSON location, and the Scheduled Task names and arguments. Existing ignore rules and delivered-alert state therefore continue to work after a switch to the 4.0 edition.

## Points to verify on a live 4.0 server

The 4.0 edition discovers what it can instead of assuming names, so each item below degrades to a log entry rather than a false alert. Confirm them during the first deployment and adjust the setting shown if needed.

| Item | Check | Setting if different |
|---|---|---|
| Instance discovery | `-ShowConfiguration` lists every instance, its `API\dbconfig.js`, and its services | `D4ABaseFolder`, `D4AInstallRoot` |
| Key source | The database result shows `key source=service environment of <API service>` or a machine environment | Run the task as `SYSTEM` |
| API port | `-ShowConfiguration` shows the expected port for each API service | `LocalApiAddress` |
| API routes | No "HTTP 404 ... route does not exist" warnings in `error_log` | `ApiAddress`, `ApplicationPerformanceEndpoints` |
| Watchdog logs | "D4A 4.0 Watchdog activity" reports the expected log file | `WatchdogLogRoot` |
| Data Collector freshness | "Data Collector SQL freshness" appears; the age matches reality during production | `DataCollectorSqlFreshnessAlerts` once validated |
| Service scope | No unexpected services in the Windows service results | An ignore rule for an intentionally stopped service |

## Validation before release

- Run the PowerShell parser on `D4A-ScheduledMonitor-4_0.ps1` and `IT_Tools_Database_Translations_and_Server_Checks.ps1` with Windows PowerShell 5.1.
- Run `D4A-ScheduledMonitor-4_0.ps1 -ShowConfiguration -SkipAutomaticUpdate` and `-ValidateConfiguration -SkipAutomaticUpdate` on a 3.9 server and on a 4.0 server.
- Run one full scan with `-DisableEmail -DisableDiscord -SkipAutomaticUpdate` on both and compare `run_log` with the 3.9 monitor. A 3.9 server must produce the same results apart from the new discovery lines.
- After publishing, confirm that a deployed 4.0 monitor reports `Monitoring version 7.13.0 is current` with channel `d4a40`.
